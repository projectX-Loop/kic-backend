# 프로젝트X Loop | KIC 대체자산 사후관리 에이전트

## 계산이 맞아도 열을 잘못 고를 수 있다

분기 성과 문단을 검토하는 운용역이 OPERF 보고서 1쪽을 연다. Advent Global Technology의 약정액과 누적 납입액이 모두 50.0이다. 누적 분배액 13.4와 잔존가치 51.8을 더해 어느 열의 50.0으로 나눠도 총가치 배수(TVPI)는 1.304배다. 답을 맞힌 시스템이 과연 납입액을 읽었다고 할 수 있을까? 이 사례 때문에 우리는 수치를 결정하는 일과 보고서에 필요한 근거를 찾는 일에 서로 다른 자유도를 주기로 했다.

## 계산에 쓴 값은 같은 판본에서 다시 찾을 수 있어야 한다

설계상 PDF를 접수하면 정해진 순서로 추출하고 검증한다. 위 사례라면 2026년 3월 31일자 해당 펀드의 ‘$50.0’을 계산용 값 50.0, 단위 백만 달러로 기록한다. 검증 결과 ID에서 분모로 쓴 관측값 ID를 따라가면 같은 판본의 ‘Total Capital Contributed’ 셀과 단위 머리글을 함께 찾을 수 있어야 한다. 이것이 정제된 입력이 제공하는 확인 경로다.

코드는 펀드·기준일·산출 기준과 금액 단위를 맞춘 뒤 십진수로 재계산한다. 필수 값이 빠지거나 납입액이 0이면 계산을 보류한다. 이 행은 계산을 마쳤고 공시값 1.30배와 0.004배 차이가 난다. 표에 표시된 금액과 배수의 자릿수가 다르므로 차이만으로 공시 오류를 단정할 수 없다. 허용오차와 반올림 정책이 정해지기까지 통과 판정도 보류한다.

## 같은 펀드라도 보고 요청이 바뀌면 다음 조회가 달라진다

분기 성과 보고를 요청하면 작성 에이전트는 저장된 검증 결과와 근거를 조회해 성과 문단을 준비한다. 같은 펀드의 정정 영향 보고를 요청하면 첫 조회 뒤에 질문이 하나 더 생긴다. “이전 값을 인용한 곳이 성과표뿐인가, 요약 문단도 바뀌어야 하나?” 계획자(Planner)가 다음에 확인할 근거와 작성할 절을 고르고 실행자(Executor)가 조회한다. 담당자는 영향받은 절의 새 초안과 기존 승인본을 비교한다.

이것이 별도 작성 요청에 Plan–Execute를 쓰려는 이유다. 대가도 있다. 같은 요청에서 조회 경로가 달라지면 엉뚱한 근거를 고르거나 필수 근거를 놓칠 수 있고, 호출마다 비용과 대기 시간이 늘어난다. 그래서 지표 정의·산식·판정·인용 가능한 판본은 코드와 입력 계약으로 고정하고 수치와 상태는 코드가 기입한다. 계획자가 근거를 확보하지 못한 항목은 미완으로 남긴다.

## 담당자가 다시 해야 하는 일이 줄어야 한다

지원 양식에서는 셀 대조, 재계산, 근거 수집과 초안 준비를 맡기는 것이 목표다. 잘못 붙인 열 이름도 유효한 ID를 가질 수 있고, 초안이 보류의 의미를 과장할 수도 있다. 담당자는 의심스러운 원문과 문장을 확인하고 승인한다. 현재 확인한 금융 사례는 사람이 식별한 OPERF 한 행의 재계산이다. 저장소에는 상태 확인 API와 그 테스트, 합성 TVPI 예시가 있다. 새 양식의 자동 추출과 보고서 작성 효과는 실험할 단계다.

**팀이 입증하려는 주장은, 수치와 판정을 고정하고 요청별 근거 조회를 허용하면 고정 조회만 쓸 때보다 필요한 인용을 덜 빠뜨리고 담당자의 원문 재확인과 초안 수정 시간이 줄어든다는 것이다.**
