# 장기 작업 위임

1. **위임 규모를 판단한다.** 요청과 관련 자료를 살피고 어떤 단계가 앞 단계의 결과에 의존하는지, 마지막에 무엇을 검증할지 파악한다. 명시적으로 호출됐어도 짧은 질문이나 단일 수정이면 장기 위임이 불필요한 이유를 한 줄로 설명하고 원래 요청을 바로 처리한다. 적합성을 묻거나 위임을 반려하는 경우, 같은 목적을 위해 함께 맡길 만한 작업 단위와 그 완료 기준을 추천한다. 제안한 추가 범위는 사용자가 선택할 때만 실행한다.
2. **끝나는 조건을 정한다.** 요청한 산출물마다 완료를 판별할 수 있는 조건과 검증 방법을 짝짓는다. 필요하면 선후 관계에 따라 작업을 나눈다. 되돌리기 쉬운 구현 선택은 합리적인 가정을 밝히고 진행한다.
3. **필요한 결정만 모은다.** 목표나 산출물이 바뀌는 선택, 접근 범위, 비용, 외부 전송, 되돌리기 어려운 조치를 먼저 살핀다. 기존 대화와 자료로 해소하고 남은 질문만 추천안과 함께 한 번에 제시한다. 목표와 권한이 충분하면 바로 착수한다. 스킬 호출로 새 권한이 생기지 않으며 도구와 저장소의 승인 절차를 그대로 따른다.
4. **합의한 범위에서 검증까지 수행한다.** 실패하면 원인을 진단하고 복구 가능한 방법으로 재시도한 뒤 완료 조건을 다시 확인한다. 이미 받은 승인은 반복해서 묻지 않는다. 새 권한이나 범위 확대가 필요해지면 해당 단계만 보류하고 독립적인 작업은 계속한다. 중간에는 방향을 바꾸는 발견이나 사용자 조치가 필요한 사항 위주로 알린다.
5. **짧게 인계한다.** 첫 문장에 완료 여부와 핵심 결과를 쓴다. 이어서 결과물 링크, 실제 수행한 검증과 결과, 중요한 가정이나 미완료 항목, 사용자가 확인하거나 결정할 사항 중 해당하는 것만 적는다. 남은 검증은 따로 밝히고 상세 로그와 이력은 필요할 때 링크한다.

## KIC 적용 예시

“PDF 판본이 뭐야?”는 바로 답할 질문이다. “PDF 판본과 검색 근거 연결 구현”을 맡기면 판본·근거 식별 방식 확인 → 검색 결과에 근거 연결 → 판본별 조회 검증을 한 작업 단위로 삼을 수 있다. 같은 문서의 두 판본에 서로 다른 근거를 두고, 각 검색 결과가 해당 판본의 원문 위치만 가리키는지 확인한다. 합성 자료로 검증했으면 실제 PDF 대조 여부를 구분해 보고한다.
